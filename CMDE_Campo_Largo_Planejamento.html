1. O que é esse sistema?

O Ministério da Educação (MEC) criou o Sistema Gestão Presente (SGP) para receber dados de todos os alunos das redes de ensino brasileiras: quem está matriculado, em qual turma, em qual escola, e com que frequência vai às aulas. Esses dados alimentam políticas públicas, entre elas o programa Pé-de-Meia.

A SEED-PR precisa enviar os dados de Campo Largo ao MEC. O problema: os dados estão espalhados — o sistema estadual (SERE) tem dados de alunos, mas as turmas, profissionais e frequências são gerenciadas pela própria prefeitura, e podem estar desatualizadas ou incorretas.

O Portal De-Para é a solução: um sistema central que puxa os dados do SERE, permite que a prefeitura de Campo Largo revise e complemente os dados, e depois envia tudo automaticamente para o SGP/MEC.

Mecanismo chave (novo na API 2.0): A prefeitura de Campo Largo assina um Termo de Autorização direto no SGP. Com isso, a SEED passa a operar em nome do município na API, usando um identificador especial (X-CODIGO-ENTIDADE) em cada requisição. Campo Largo não precisa de credenciais de API próprias.

3. Fluxo do processo — passo a passo
Como os dados percorrem o sistema, do SERE ao SGP/MEC
SEED / CODIS
Portal De-Para (Sistema)
Campo Largo (Município)
Etapa 1

Extração do SERE

Script Python lê os dados de alunos, matrículas e estabelecimentos de Campo Largo no SERE e carrega no banco de trabalho.

Etapa 2

Filtragem e elegibilidade

O sistema separa apenas matrículas com etapa de ensino válida na API 2.0, descartando o que não pode ser enviado.

Etapa 3

Abertura do ciclo de validação

SEED abre um ciclo para Campo Largo 2026. O portal disponibiliza os dados e os modelos de planilha para o município.

Etapa 4

Município acessa o portal

Gestor de Campo Largo recebe acesso e visualiza todos os alunos, turmas e matrículas pré-carregados do SERE.

Etapa 5

Preenchimento das planilhas

Município baixa e preenche as planilhas-modelo: Profissionais, Turmas extras (não existentes no SERE) e Frequências das escolas sem RCO.

Etapa 6

Upload e correção de dados

Município faz upload das planilhas e corrige os dados de alunos diretamente no portal (CPF, nome, data de nascimento etc.).

Etapa 7

Validação automática

O sistema valida automaticamente CPF, campos obrigatórios e domínios da API. Inconsistências são marcadas em vermelho diretamente na tela.

Etapa 8

Correção das inconsistências

Município resolve os erros apontados, substituindo ou confirmando cada dado. O portal não avança enquanto houver pendências críticas.

Etapa 9

Confirmação pelo município

Gestor confirma formalmente que os dados estão corretos e submete o ciclo para análise da SEED.

Etapa 10

Homologação pela SEED

Analista da SEED revisa o pacote de dados confirmado pelo município e libera para envio ao SGP.

Etapa 11

Envio à API CMDE 2.0

Scripts enviam na ordem hierárquica: Escolas → Turmas → Estudantes + matrículas → Frequências → Desfechos. Cada requisição usa o cabeçalho X-CODIGO-ENTIDADE do município.

Etapa 12

Monitoramento e relatório

Portal exibe status de cada lote enviado. Erros são registrados e podem ser reprocessados. SEED confirma a conclusão do envio.

4. Regra das matrículas — o que muda na API 2.0?

Na versão 2.0 do SGP, um aluno pode ter múltiplas matrículas ativas simultaneamente — cada uma vinculada a uma turma diferente. Isso espelha a realidade: o mesmo aluno pode estar matriculado no ensino regular e em uma atividade de reforço ou AEE ao mesmo tempo.

Situação do aluno no SEREO que fazemos na API 2.0
Matrícula no EF, EM ou EJA com etapa válida na APIENVIA — Todas as matrículas com etapa mapeável
Matrícula em curso complementar COM etapa válida (ex: AEE)ENVIA — A API 2.0 aceita; o SGP classifica a elegibilidade internamente
Matrícula em curso SEM etapa válida na API (ex: línguas, esporte)NÃO ENVIA — Não há campo no schema para esse tipo
Matrícula cancelada / excluída por erro no SERENÃO ENVIA — Filtro de elegibilidade exclui automaticamente

7. Pontos em aberto — itens para definição na reunião
1
Autorização / API

Campo Largo já assinou o Termo de Autorização no SGP?

Sem o termo assinado pelo município, a SEED não pode enviar dados em nome de Campo Largo. Precisa ser no nível Completa (permite_escrita = true). Quem aciona o município para assinar?

2
Escopo / Dados

Quais escolas de Campo Largo entram no piloto?

Todas as escolas municipais? Apenas algumas? Há escolas privadas conveniadas que também precisam ser enviadas?

3
Pessoas / Responsabilidade

Quem é o responsável técnico pelo lado do município?

Precisamos de um nome, cargo, e-mail e telefone do gestor de Campo Largo que irá acessar o portal e preencher as planilhas. Quem define isso?

4
Prazo

Qual o prazo limite para os dados de 2026 estarem no SGP?

O MEC tem janelas de envio mensais. Qual o primeiro mês-alvo? Março/2026? Abril? Definir prazo retroativo para os dados já existentes.

5
Frequência

Quais escolas de Campo Largo usam o RCO?

Para escolas com RCO, a frequência pode ser extraída automaticamente. Para as demais, o município precisa preencher a planilha de frequências manualmente. Precisamos levantar isso escola por escola.

6
Dados / SERE

As turmas de Campo Largo estão no SERE?

Se sim, podemos pre-carregar. Se não (escola gerencia no sistema local), o município terá de criar todas as turmas via planilha — o que aumenta o esforço. Qual a situação atual?

7
Matrículas / Regras

Quais modalidades/cursos de Campo Largo devem ou não ser enviados?

Com a API 2.0 aceitando múltiplas matrículas, precisamos revisar o catálogo de exclusão. Cursos de língua e esporte não têm etapa mapeável na API — confirmar com DPGE quais outros cursos seguem a mesma regra.

8
Processo

O envio será mensal (contínuo) ou apenas carga inicial?

A API 2.0 exige atualização mensal das frequências. O Portal De-Para precisa ser operado mensalmente ou apenas uma vez? Definir se o processo é periódico ou pontual para 2026.
